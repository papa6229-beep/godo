# 상품팀 일일 재고점검 내부 업무 설계

작성일: 2026-07-30  
상태: 사용자 승인 설계  
대상: `task-product-daily` 한 건  
근거: `docs/governance/DECISIONS.md` D-009

## 1. 목적

새 고도몰 키와 실제 판매상품이 준비되기 전에도, 고도몰 스펙에 맞춘 시험자료로 상품팀의 대표 업무를 미리 만들고 검증한다.

이번 업무는 **상품팀 내부의 일상 점검**이다. HQ가 모든 팀의 사소한 일상 업무를 자동으로 보고받거나 승인하게 만들지 않는다.

## 2. 확정된 업무 원칙

HQ가 팀의 업무 내용을 받는 경우는 두 가지뿐이다.

1. HQ가 특정 업무를 지시하고 결과 보고를 요청한 경우
2. 팀장이 보고할 필요가 있다고 판단해 직접 HQ에 보고한 경우

그 밖의 팀 내부 일상 업무는 팀 안에서 처리·기록한다. HQ는 각 팀의 업무 현황과 기록을 원할 때 직접 열람할 수 있다.

## 3. 검토한 접근

### 접근 A — 팀 내부에서 종료하고 HQ는 필요할 때 열람

- 일상 업무는 팀장 확인으로 끝낸다.
- HQ 알림함이나 승인 대기열에 자동으로 올리지 않는다.
- HQ는 부서 관제 화면과 업무 기록에서 필요할 때 확인한다.

**채택.** HQ의 불필요한 보고·승인 피로를 막고 사용자 의도와 가장 잘 맞는다.

### 접근 B — 모든 일상 보고를 HQ에 보내되 승인은 생략

- 구현은 단순하지만 HQ 알림이 사소한 업무로 쌓인다.
- “모든 일상 업무를 자동 보고받을 필요가 없다”는 사용자 의도와 맞지 않는다.

**기각.**

### 접근 C — 모든 자동 업무에 상세 보고 정책을 즉시 추가

- 장기적으로 유연하지만 현재 업무 한 건을 위해 전체 스펙과 화면을 확대해야 한다.
- 업무 종류가 늘어나 실제 필요가 확인될 때 도입해도 늦지 않다.

**이번 범위에서는 기각.**

## 4. 사용자 흐름

### 4.1 상품팀 내부 일일 점검

1. 상품팀장이 상품팀 화면의 `재고·매출 일일 점검`에서 `지금 점검`을 누른다.
2. 상품 관리 AI가 공통 데이터 스냅샷과 `inventoryRiskContract`를 사용해 재고위험 결과를 만든다.
3. 결과에는 반드시 `실제 데이터`·`시험 데이터`·`연결 안 됨` 중 올바른 출처가 표시된다.
4. 상품팀장은 결과를 확인한다.
5. 이상이 없으면 `확인 완료`한다.
6. 승인하지 않으면 이유 한 문장을 입력하고 반려한다.
7. 결과·결정·실제 로그인한 행위자·시각이 상품팀 업무 기록에 남는다.
8. HQ에는 자동 메시지나 승인 요청을 만들지 않는다.

### 4.2 HQ가 먼저 요청한 업무

기존 B-use 흐름을 그대로 사용한다.

`HQ 지시 → 상품팀 수행 → 결과 제출 → HQ 확인 → 기록`

이번 설계는 이 흐름을 변경하지 않는다.

### 4.3 상품팀장이 자발적으로 HQ에 보고

상품팀장은 내부 업무 결과 중 HQ에 알릴 가치가 있다고 판단한 것만 별도의 `HQ에 보고` 동작으로 보낸다.

이번 구현에서는 새로운 포괄적 보고 편집기를 만들지 않는다. 기존 팀 메시지·보고 경로를 재사용할 수 있는지 먼저 확인하고, 재사용할 수 없다면 이 동작은 후속 항목으로 명시한다. 내부 점검 완료를 HQ 보고 구현에 묶어 지연시키지 않는다.

## 5. 데이터와 출처

- 계산은 `buildDepartmentSourceOfTruthSnapshot`과 `inventoryRiskContract`만 사용한다.
- 재고위험 임계값이나 집계식을 새로 만들지 않는다.
- `DepartmentSourceOfTruthSnapshot.sourceMode` 등 기존 출처 정본을 실행 결과까지 전달한다.
- 현재 시험자료로 실행한 결과는 반드시 `시험 데이터`로 표시한다.
- 출처를 `standing.source` 유무나 버튼 이름으로 추측하지 않는다.
- 데이터가 준비되지 않았거나 출처를 확정할 수 없으면 실제 데이터로 표시하지 않는다.
- 실제 상품이 등록되면 같은 경로의 입력만 실제 데이터로 바꾸어 재시험한다.

## 6. 상태와 기록

현재 `AgentTaskPanel`의 승인 대기와 완료 상태는 React 메모리에만 있어 새로고침하면 사라진다. 대표 업무에서는 이를 허용하지 않는다.

- 반복 AI 업무의 실행 상태 정본은 이미 `AgentTaskRunner`와 HQ 부서 관제 화면이 함께 쓰는 append-only `activityLedger`로 고정한다. 조회·구독은 `activityLedgerRepository`를 통해서만 한다.
- `taskLifecycleAppAdapter`는 HQ 지시·팀 간 협업처럼 사람의 지시→수행→결과→승인 흐름에 계속 사용하며, 이번 팀 내부 반복 점검을 그곳에 중복 등록하지 않는다.
- 새 저장 체계를 만들지 않는다.
- 상태는 최소한 `점검 전 → 확인 대기 → 확인 완료` 또는 `반려`를 구분한다.
- 새로고침·탭 이동·같은 계정 재진입 뒤에도 같은 상태를 복원한다.
- `취소`가 화면만 닫고 원장에는 대기를 남기는 상태를 허용하지 않는다.
- 중복 클릭으로 같은 점검·메시지·원장 기록이 두 번 생기지 않아야 한다.
- 이번 단계의 저장은 기존 localStorage 어댑터를 사용하며, 서버 DB 완료로 표현하지 않는다.

## 7. 행위자와 권한

- 실행·확인·반려는 상품팀 팀장만 할 수 있다.
- HQ와 다른 팀은 열람만 가능하다.
- AI의 계산 행위는 agent actor로 기록한다.
- 사람의 확인·반려는 실제 로그인한 `identity.actor`를 기록한다.
- `'운영자'` 같은 하드코딩 사람 라벨을 새 기록에 사용하지 않는다.

## 8. HQ 노출 정책

- 상품팀 내부 일일 점검은 HQ 알림함·승인 대기열·팀 메시지 수신함에 자동 생성하지 않는다.
- HQ가 필요할 때 부서 관제 화면에서 상품팀의 최근 점검 상태와 기록을 열람할 수 있어야 한다.
- 이 열람은 새로운 승인 업무를 만들지 않는다.
- HQ가 직접 지시한 업무와 팀장이 명시적으로 보낸 보고는 기존처럼 HQ에 도착한다.

## 9. 오류 처리

- 데이터 없음: `데이터가 준비되지 않아 점검하지 못했습니다`로 남기고 완료 처리하지 않는다.
- 출처 계약이 `unavailable`이면 `연결 안 됨`으로 남긴다. 계산·저장 자체가 실패하면 `실패`로 남긴다. 둘 다 실제 데이터나 완료로 표시하지 않는다.
- 저장 실패: 입력과 계산 결과를 화면에 유지하고 성공으로 표시하지 않는다.
- 권한 불일치: 버튼 숨김뿐 아니라 실행 함수에서도 거부한다.
- 반려 이유 없음: 반려를 거부하고 한 문장 입력을 안내한다.

## 10. 검증

구현 작업자는 먼저 기존 검사를 확장해 RED를 확인하고 구현 후 GREEN을 확인한다.

필수 자동검사:

1. 시험자료 결과가 `시험 데이터`로 표시된다.
2. 실제 데이터·시험 데이터·연결 안 됨이 서로 바뀌지 않는다.
3. 상품팀 팀장만 실행·확인·반려할 수 있다.
4. 확인 대기 상태가 새로고침 뒤 복원된다.
5. 확인 완료·반려 상태와 이유가 복원된다.
6. 실제 로그인한 행위자가 기록된다.
7. 내부 일일 점검은 HQ 메시지·승인 업무를 만들지 않는다.
8. HQ 지시 업무의 기존 회신·승인 흐름은 유지된다.
9. 중복 실행·중복 기록이 생기지 않는다.
10. 데이터 없음·저장 실패를 완료로 표시하지 않는다.

구현자는 집중검사와 관련 타입·lint만 실행한다. 전체 `npm test`는 Codex가 이 작업 경계에서 한 번 실행한다.

화면 동작이 바뀌므로 자동검사 통과 뒤 실제 진입 화면 검증이 필요하다. 다만 Preview/Vercel 확인은 로컬·코드 검증을 먼저 마친 뒤 화면 실증이 필요한 시점에 한 번만 수행한다.

## 11. 이번 범위 밖

- 예약 시각 자동 실행
- 서버 DB·최종 서버 선택
- 고도몰 키·환경변수 연결
- 실제 상품 등록
- 외부 WRITE
- 모든 팀 자동 업무의 공통 보고정책 재설계
- CS·마케팅·디자인팀 대표 업무
- Production 배포

## 12. 완료 조건

다음을 모두 만족하면 이번 **미리 구현·시험** 묶음을 완료로 판정한다.

1. 상품팀장이 시험자료로 일일 재고점검을 실행한다.
2. 결과가 시험자료임을 명확히 표시한다.
3. 상품팀장이 확인 완료하거나 이유 한 문장으로 반려한다.
4. 새로고침 뒤에도 결과·상태·행위자·이유가 남는다.
5. HQ에 자동 보고·승인 요청이 생기지 않는다.
6. HQ는 원할 때 상품팀 업무 기록을 열람할 수 있다.
7. 기존 HQ 지시 업무 흐름은 회귀하지 않는다.
8. 집중검사와 전체 회귀 게이트가 통과한다.

이 완료는 **시험자료 기반 미리 구현 완료**다. 실제 상품·실제 데이터로 같은 흐름을 재시험하기 전에는 E 또는 F의 실제 완주로 표시하지 않는다.
